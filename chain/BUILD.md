# Program build and live setup

The program ID is supplied at runtime. There is no declare_id constant or deployment key committed. `programs/kontor/src/lib.rs` uses exact solana-program 2.3.0, SPL Token 8.0.0 and Borsh 1.5.7. Heavy builds run only on the approved disposable runner.

1. Install the pinned, verified prebuilt Agave release on Ubuntu (parent owns workflow/download verification). Run `bash scripts/chain-build.sh`. Output: `programs/kontor/target/deploy/kontor.so`. Retain `.so`, SHA256, resolved Cargo.lock, source commit and toolchain versions in the separately labeled standard build artifact. The verified first-build Cargo.lock is now retained; subsequent builds use --locked. Agave 4.1.2 compiled the program successfully; the earlier 2.3.13 toolchain could not parse a transitive edition-2024 manifest.
2. Start a validator for the actual compiled-program integration test: `solana-test-validator --reset --quiet --ledger /tmp/kontor-ledger --bpf-program PROGRAM_ID programs/kontor/target/deploy/kontor.so`. Use a generated public program ID from an external keypair. After health, run `KONTOR_RPC_URL=http://127.0.0.1:8899 KONTOR_PROGRAM_ID=PROGRAM_ID KONTOR_KEY_DIR=/tmp/kontor-test-keys node scripts/chain-selftest.mjs`. Preserve its public JSON output as actual SBF evidence; it is not a JS model.
3. For devnet, parent generates private deployer/program keys outside git and obtains free test SOL. Determine required rent from binary size. Deploy with explicit `--url devnet --keypair DEPLOYER --program-id PROGRAM_KEY` using `solana program deploy ...`. Do not change global CLI configuration. Retain upgrade authority and disclose it as trusted.
4. Operator keys live in a excluded directory with mode 0700. `loadOrCreateKeys(directory)` creates registrar/reviewer/approverA/approverB/executor/recipientOwner/mint key files with mode 0600, or loads them on restart. Prepopulate registrar.json with the funded devnet deployer key if desired. Otherwise fund registrar before setup. No secret is returned by setup logs or the public manifest.
5. `KONTOR_RPC_URL=https://api.devnet.solana.com KONTOR_PROGRAM_ID=... KONTOR_KEY_DIR=/private/path KONTOR_MANIFEST_PATH=/private/path/scenario.json node scripts/chain-setup.mjs` creates a custom six-decimal Test USD mint, supplier recipient account and separate registrar-owned treasury token account, funds fee-payer roles from registrar (up to 0.03 test SOL each), configures roles, creates a fresh obligation/vault and issues 1,000 Test USD to the vault. The account is program-controlled. Issuing synthetic tokens does not grant withdrawal power.
6. Load manifest and same key directory in the server; call createClient with manifest fields and keys. `read` verifies immutable configuration matches expected roles/mint/treasury and each obligation recipient. Reset creates/funds a new scenario, never alters the old one.
7. For a deterministic live proof use `scripts/chain-selftest.mjs` with `KONTOR_ALLOW_DEVNET=1` only when enough test SOL is available, or the narrower `scripts/chain-proof.mjs`. Never publish secrets. Failed transactions charge test SOL; the control claim concerns zero Test USD movement.

No fallback creates a fake explorer signature. Network/script failures are incomplete evidence, not successful on-chain demonstrations. Custom mint is never labeled USDC. Config registrar, reviewer, two approvers, mint, treasury token account and treasury owner are immutable. Recipient account and token owner are immutable per obligation; separate obligations under one config can use different recipients. Exactly one credit is supported in this prototype. Anyone may execute a currently fully authorized payment while paying their own fees; executor identity is not an authorization bypass. After payment, any signed caller may return the actual remaining vault balance only to the configured treasury. Empty returns are valid no-ops and later donations can be returned again; this never reopens supplier payment. There is no unpaid withdrawal, cancellation or arbitrary destination.

## Unknown outcomes

The server intentionally blocks every mutation while an operation is pending/unknown. It does not silently retry. To inspect the exact recorded signature and current on-chain state without changing either, run `KONTOR_MANIFEST_PATH=/private/path/scenario.json node scripts/chain-reconcile.mjs > /private/path/reconciliation.json`. This reads journals, signature history, confirmed logs and balances. It does **not** clear the guard. The controller must compare those results with the saved invoice/approval/settlement evidence and update the service state explicitly; absent RPC history alone is never permission to resend. Do not describe this manual recovery boundary as automatic reconciliation.

## V2 rollout boundary

Use a fresh program key and new manifest for Config `KNTRCFG2` / Obligation `KNTROBL2`. Do not upgrade the historical v1 program in place: old config bytes mean a different destination, and old obligations lack recipient fields. Preserve v1 transaction evidence unchanged and label it by program version; its remaining vault balance is not migrated by a v2 deployment. Verify current deployment status and exact program ID from the published product proof rather than assuming source changes are live.

The compiled-program selftest uses fresh isolated keys and a test-only freeze-authorized mint to exercise frozen recipient/treasury rejection. Normal setup minting has no freeze authority. Pass `KONTOR_EVIDENCE_PATH` outside the product tree; the default is the external test-key directory. The expanded checks exercise paid-only return, fixed destination/owner/mint, two suppliers, empty repeat, donated dust and overfunded no-credit remainder. Run Rust formatting and `cargo fmt --check` alongside the existing build gates.
